Input NeXus Formatting#

The current file configuration used by QENSfitter4D utilizes a core NXroot filetype with data stored within NXentries in the form of an NXdata type. The power of NeXus data allows for multiple entries – which can be used for multiple energies and/or temperatures – or one can load in multiple files with single entries per file.

Note

It is important however to separate the data by at least entry level partitions as the results are stored in the same entry as the dataset. By separating them we can avoid overlapping stored results and fitting conditions.

It is also usefull to include a properly generated NXsample in the entry. Future versions of this software will include symmetrization options which will rely on the NXsample defined symmetries.

Data Format#

The most important thing to keep in mind when formatting your data is to ensure that (in numpy terms) the energy axis is the ‘zero’ axis. The precise order of the reciprocal space dimensions is not important, however for consistency the numpy dimension order this software assumes is [dE,Ql,Qk,Qh].

Danger

Any results will be saved under the assumption the dimensions follow the schema [dE,Ql,Qk,Qh]. It is important to be aware that if these axis are rotated or in a different order the software isn’t currently written to handle these cases directly. These scenarios may require post-fitting edits or additional developement for handling these cases. As of 0.1.0 however, this has not been a high priority.

Formatting From MDHisto#

One popular data output format – used at sources like the Spallation Neutron Source at Oak Ridge National Laboratory – is the MDHisto format. In order to analyze this data one must first wrap the data. Below is an example script of how one might wrap an MDHisto file into a nexus file format.

 1def mdhistoQENS(MDHistofile,sample='sample',temperature=280,
 2                energy='energy',lattice_centering='P',
 3                laue_group='-1',unit_cell_group='cubic'):
 4    space_group = lattice_centering+' '+laue_group
 5    root_name = sample + "_QENS"
 6    entry_name = energy+f"meV_{temperature}K"
 7
 8    MDsample = MDHistofile.MDHistoWorkspace.experiment0.sample.oriented_lattice
 9    a = MDsample.unit_cell_a
10    alpha = MDsample.unit_cell_alpha
11    b = MDsample.unit_cell_b
12    beta = MDsample.unit_cell_beta
13    c = MDsample.unit_cell_c
14    gamma = MDsample.unit_cell_gamma
15
16    sample = NXsample(chemical_formula=root_name,
17                lattice_centring=lattice_centering,
18                laue_group=laue_group,
19                space_group=space_group,
20                temperature=temperature,
21                unit_cell_group=unit_cell_group,
22                unitcell_a=a,
23                unit_cell_alpha=alpha,
24                unitcell_b=b,
25                unitcell_beta=beta,
26                unitcell_c=c,
27                unitcell_gamma=gamma)
28
29
30    data = MDHistofile.MDHistoWorkspace.data
31    signal = data.signal
32    H = data.D0
33    K = data.D1
34    L = data.D2
35    E = data.D3
36
37    nxtree[root_name]=NXroot()
38    nxtree[root_name][entry_name]=NXentry()
39    nxtree[root_name][entry_name]['sample']=sample
40    try:
41        # In case error calculations were included in your data reduction script
42        errors  = data.errors_squared
43        nxtree[root_name][entry_name]['transform']=NXdata(signal,[E,L,K,H],errors=np.sqrt(errors))
44        nxtree[root_name][entry_name]['transform']['errors_squared'].rename('errors')
45    except:
46        # Otherwise, for in case error calculations were not included in your data reduction script
47        nxtree[root_name][entry_name]['transform']=NXdata(signal,[E,L,K,H])
48    nxtree[root_name][entry_name]['transform']['D0'].rename('Qh')
49    nxtree[root_name][entry_name]['transform']['D1'].rename('Qk')
50    nxtree[root_name][entry_name]['transform']['D2'].rename('Ql')
51    nxtree[root_name][entry_name]['transform']['D3'].rename('E')

Caution

This is the axes naming schema the author used. Optimally all functions should opperate agnostically of axes naming schema, but it is possible that this is not the case as of version 0.1.0. Please report any errors caused by axes name inconsistencies.
